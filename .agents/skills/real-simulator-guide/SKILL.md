# Real Simulator — гид ассистента

Локальный симулятор социальных ИИ-агентов: персонажи с характерами, инструментами
и скрытыми целями общаются и действуют в сценах; каждый персонаж работает на
своей модели (LM Studio / OpenRouter / любой OpenAI-совместимый endpoint / Mock).
Судьи и LLM-оценщика нет — оценщиком выступает пользователь (или схемы валидации).

Проект: `D:\Project\AI\real-simulator`. Два канонических документа в корне:
`README.md` — полный мануал пользователя; `AGENTS.md` — архитектура и правила
правок кода. Этот навык — выжимка «как помогать», детали в `references/`.

## Запуск и проверка доступа

- Разработка: `npm run dev -- -p 3999` (порт 3000 на этой машине занят другим
  процессом — всегда указывай порт явно).
- Продакшн локально: `start.bat` (меню: start | stop | restart | status | log).
- Портативный релиз на чужой ПК: `node scripts/make-release.mjs` → папка `release/`.
- Node.js 22.13+. Веб-UI и REST API на одном порту: `http://localhost:3999`.
- Проверка живости: `curl -s http://localhost:3999/api/stats`.

## Карта мира

| Понятие | Суть |
|---|---|
| **Провайдер** | endpoint с моделями: `lmstudio`, `openrouter`, `openai-compatible`, `mock`. Ключи хранятся в БД без шифрования. |
| **Персонаж** | имя + emoji + persona + модель (providerId, model, temperature, maxTokens) + инструменты (toolIds) + свободный JSON `state` + доход `income` + границы `boundaries`. `isHuman: true` — им управляет пользователь, модель не нужна. |
| **Сцена** | упорядоченные участники, обстановка `setting`, `config` (место `place`, лимиты, пауза для человека…), **личная цель** каждому участнику (`goals`) и привязка схемы валидации (`schemas`). |
| **Инструмент** | только декларативные данные, не код: JSON-схема параметров, видимость, шаблон наблюдения, эффекты на state, цена $, тренировка навыка, исходы. Исполнитель один — `executeTool`. |
| **Аудитория события** | `all` / `target` / `self` / `none`. Главный инвариант: агент видит только публичные события, адресованные ему и свои действия. |
| **Характеристики** | реестр полей state. `public` — видны всем в строке участника; `hidden` — только владельцу; о чужих скрытых — только через «знания». Эффекты клампятся по min/max реестра. |
| **Навыки** | скрытая характеристика `skill_<key>` (0..maxLevel) + счётчик практики: N успешных применений тула с «тренирует навык» = +1 уровень. |
| **Границы (согласие)** | правила владельца на адресные тула: minRelation, minMood, requirePlace, requireAttr. Проверка fail-closed до денег и эффектов; отказ не виден другим, границы никогда не показываются в промптах. |
| **Знания и ложь** | истина о hidden-атрибуте живёт у владельца; у наблюдателя — `claimed` (заявление, можно лгать) или `verified` (проверено физикой). Ложь вскрывается проверкой → штраф `liePenalty`. |
| **Отношения** | направленная матрица «X→Y» (−10..10), агент видит только свои чувства. Химия пары (−3..+3, симметричная, скрытая) умножает изменения отношений на `1 + химия/2`. |
| **Магазин** | товары — карточки с ценой/эффектами/слотом одежды/задержкой в сценах. Агентам автоматически дают `shop_browse` и `shop_buy`. |
| **Одежда** | слоты с слоями (1 верх / 2 бельё) и местами обнажения. Виртуальные тула `undress`/`wear`; обнажение верифицирует скрытые атрибуты, которые слот прикрывал. |
| **Исходы** | условия по истинным значениям → эффекты + личная заметка цели. Сработавший `outcomeId` доступен условиям флоу («финал только после оргазма»). |
| **Схемы валидации** | «e2e-тесты персонажа»: цепочка шагов из tool-вызовов (порядок важен), forbidden-тулы, штраф. Привязывается к участнику сцены; скоринг — пост-фактум по логу событий. |
| **Сценарии (флоу)** | канвас: узлы `scene`/`final`/`exit`, рёбра с условиями (шаг, скор, без нарушений, state, relation, outcome). Прогон ведёт состав по графу, между сценами — личный рекап. |
| **`request_tool`** | виртуальный тул (при включённой опции сцены): агент просит новый инструмент, пользователь одобряет/отклоняет; одобренный создаётся в БД сразу. |

## Как помогать: порядок работы

Типовая задача пользователя — «настроить мир и прогнать сцену». Действуй по цепочке:

1. **Уточни замысел**: кто участвует, где (место), чего каждый хочет добиться,
   чем измеряем успех. Из этого выводится всё остальное.
2. **Провайдер** — если нет ни одного (`GET /api/providers`): LM Studio локально
   (ключ не нужен) или OpenRouter (нужен ключ). Для проверки механики без
   LLM — провайдер `mock`. Проверка соединения:
   `GET /api/providers/:id/models?test=1`.
3. **Реестры** под сценарий: характеристики, навыки, места, слоты одежды,
   товары, инструменты. Не плодите сущности впрок — только то, что нужно сцене.
4. **Персонажи**: persona (советы ниже), модель, maxTokens ≥ 1500 для думающих
   моделей, state с стартовыми значениями атрибутов (включая `money`),
   границы на чувствительные действия, назначь инструменты.
5. **Сцена**: участники в порядке ходов, `config.place` (важно для границ и
   одежды), `goals` каждому — конкретные и личные, `schemas` для проверки,
   `pauseForHumans` если пользователь играет сам.
6. **Запуск и наблюдение**: `POST /api/scenes/:id/control {"action":"start"}`;
   лента `GET /api/scenes/:id/events` или SSE `/api/stream`. Вмешательство:
   `inject` (режиссёрское событие), `say` (реплика за человека/кукловод),
   `act` (ручной вызов тула). При `pauseForHumans` сцена после хода человека
   (say/act) продолжает **сама** — ручной resume после каждого хода не нужен.
7. **Оценка**: `GET /api/scenes/:id/scores` (пересчёт живой, схему можно править
   и после завершения сцены). Для флоу — отчёт прогона.

## Советы, которые стоит давать пользователю

- **Persona**: 3–8 конкретных предложений — характер, речь (словечки, манера),
  фон, чего хочет, в чём противоречие. Плохо: «девушка 25 лет». Хорошо:
  «Яна, 24, бариста; говорит быстро, сыплет сленгом кофейни, боится
  показаться наивной; за словом в карман не лезет, но краснеет от комплиментов».
- **Цели сцены** — личные и проверяемые действиями: «узнать, где Саша был
  вчера, не выдав интереса напрямую», а не «пообщаться».
- **Инструменты**: адресным действиям — `audience: "target"` + `targetParam`;
  не выдавай персонажу лишних тулов. Цена и границы — на сильные действия.
  Имя тула — только `a-z0-9_` (slug); русское название — в `title`.
- **Думающие модели** (Qwen3 и т.п.): maxTokens ≥ 1500–2048, иначе tool-вызовы
  приходят пустыми; 20–60 секунд на ход — норма.
- **Деньги**: сведи доход и цены — студентка с $100/мес не должна покупать
  салон красоты; нехватка денег = отказ действия, это фича.
- **Проверка механики без LLM**: провайдер `mock` или `npm run e2e`.

## Отладка

Главный инструмент — инспектор хода: в live-комнате кнопка `{}` у события
(или `GET /api/scenes/:id/apilogs`) показывает точный промпт и сырой ответ
модели. Если агент «не видит» событие — это почти всегда аудитория (см.
инвариант видимости), а не баг. Типовые поломки и лечение —
[references/troubleshooting.md](references/troubleshooting.md).

## Если пользователь просит изменить код

Сначала прочитай `AGENTS.md` в корне — там канон архитектуры. Критичные
инварианты: видимость событий строит `prompt.ts:buildMessages` и нарушать её
нельзя; модельные вызовы и ручные действия идут через один `executeTool`;
тулы — данные, не код; синглтоны БД/движка живут на `globalThis` (HMR);
UI тёмный, нативные `<select>` запрещены; комментарии и строки — на русском.
Перед сдачей: `npx tsc --noEmit` и `npm run e2e` (движок на mock-провайдере).

## Безопасность

`data/` содержит **незашифрованные API-ключи** и живую БД пользователя —
никогда не публикуй, не коммить и не отправляй куда-либо. Не пиши в БД
напрямую скриптами: только через REST API или с `SIM_DB_PATH` на отдельный файл.
