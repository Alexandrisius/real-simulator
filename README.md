# Real Simulator

Локальный симулятор социальных ИИ-агентов. Вы создаёте персонажей с характерами,
инструментами и целями, собираете их в сцены — и наблюдаете, как они общаются
и действуют друг с другом. Каждый персонаж может работать на **своей модели**
(LM Studio локально, OpenRouter или любой OpenAI-совместимый сервер) — и вы
сравниваете, кто как ведёт себя в одинаковых условиях.

Никакого скоринга и модели-судьи нет: **судья — вы**. Приложение лишь честно
фиксирует контекст каждого агента и показывает всё, что происходит.

## Возможности

- **Персонажи**: имя, аватар, persona (характер/привычки/цели), своя модель и
  провайдер, температура, свой набор инструментов, свободное JSON-состояние
  (настроение, отношения, одежда — что угодно).
- **Личные цели в сцене**: каждому участнику сцены задаётся своя цель — она
  попадает только в его system prompt (остальные о ней не знают) и держится
  весь сценарий, а не вылетает за окно контекста, как указание режиссёра.
  Локация = сеттинг сцены: «В кафе», «Дома вечером» — разные сцены с разными
  целями у тех же персонажей.
- **Инструменты** (native function calling): любое действие настраивается через
  UI — JSON-схема параметров, описание для модели, видимость действия
  (всем / только получателю / только актёру / скрытое), шаблон «наблюдения»
  для остальных участников и эффекты на состояние персонажей.
- **Сцены**: любое число участников, порядок ходов, обстановка, доп. правила,
  скорость (пауза между ходами), лимит ходов.
- **Контекст по-честному**: каждый агент видит только то, что должен видеть —
  публичные события, адресованные лично ему сообщения и собственные действия.
  Личные сообщения других он не видит, как в жизни.
- **Live-комната**: транскрипт переписки и действий в реальном времени (SSE),
  управление (старт/пауза/шаг/стоп), «режиссёрские» указания всем или лично
  персонажу, инспектор промптов (точные `messages` и ответ модели за каждый ход).
- **Режим человека**: любой персонаж можно пометить как «управляется вами» —
  движок не играет за него, а вы пишете за него реплики и вручную вызываетаете
  его инструменты (диалог с поиском, формой аргументов и эффектами). Можно и
  «кукловодить» ИИ-персонажами. Опция сцены «пауза для человека» ставит сцену
  на паузу после каждого круга ИИ. Сцена из одного ИИ-агента + вы-архитектор
  тоже полноценный сценарий.
- **Сценарии (канвас)**: цепочки сцен на графе — узлы-сцены, финалы и выходы,
  рёбра с машиночитаемыми условиями перехода («Саша обязан поцеловать Яну —
  иначе провал»). Прогон показывает, кто из персонажей дойдёт до финала,
  с очками за сцены и бонусами за узлы.
- **Заявки на инструменты**: включите опцию сцены — и агенты смогут просить
  у вас (архитектора) новые инструменты прямо по ходу сцены через
  `request_tool`. Черновик проходит структурную проверку, вы одобряете
  или отклоняете в один клик; одобренный инструмент создаётся в БД и
  доступен агенту уже со следующего хода.
- **Экономика**: у инструментов есть цена ($), у персонажей — доход.
  Деньги живут в ключе `money` состояния, списываются при платных действиях,
  доход начисляется при переходах между сценами сценария. Студентка за $100/мес
  не сможет позволить себе салон красоты — а топ-менеджер сможет.
- **Провайдеры**: LM Studio, OpenRouter, любой OpenAI-совместимый endpoint
  и встроенный Mock для проверки всего без модели.

## Запуск

Требуется Node.js 22.13+ (проверено на 24.x).

```bash
npm install
npm run dev
# открыть http://localhost:3000
```

Продакшн-режим: `npm run build && npm start`. E2E-тест движка (без модели):
`npm run e2e`. База — SQLite, создаётся автоматически в `data/app.db`
(переменная `SIM_DB_PATH` переопределяет путь).

**Windows + антивирус/прокси с перехватом TLS**: если OpenRouter отдаёт
`self-signed certificate in certificate chain`, запускайте сервер с
`NODE_USE_SYSTEM_CA=1` (Node будет доверять корпоративным корням из
хранилища Windows):

```bash
NODE_USE_SYSTEM_CA=1 npm run dev
```

Если это не помогло (DLP-система подменяет сертификаты своим корнем), на
странице «Провайдеры» внизу есть **«Корпоративный режим»** — тумблер, полностью
отключающий проверку SSL-сертификатов у исходящих вызовов провайдеров.
Действует сразу, без перезапуска; включайте только в доверенной сети.

**Думающие модели (Qwen3 и т.п.)**: рассуждения (`reasoning_tokens`) съедают
бюджет ответа — ставьте «Макс. токенов» ≥ 1500–2048, иначе получите пустой
ответ без вызова инструмента. Такие модели отвечают 20–60 секунд на ход —
это нормально.

## Подключение моделей

### LM Studio (локально, бесплатно)

1. Загрузите модель с поддержкой tools (например, Qwen3, Llama 3.1+).
2. Developer → **Start Server** (порт по умолчанию 1234).
3. В приложении: Провайдеры → Добавить → тип «LM Studio»,
   URL `http://localhost:1234/v1`. Ключ не нужен.
4. В редакторе персонажа нажмите ⟳ — список моделей подтянется сам.

### OpenRouter (сотни моделей по одному ключу)

1. Получите ключ на [openrouter.ai/keys](https://openrouter.ai/keys).
2. Провайдеры → Добавить → тип «OpenRouter»,
   URL `https://openrouter.ai/api/v1`, вставьте ключ.
3. Модель указывается в формате `vendor/name`, например
   `qwen/qwen-3-235b-a22b-instruct`, `mistralai/mistral-nemo` — список
   подтягивается автоматически, но можно вписать и вручную.

Ключи хранятся в локальной SQLite-базе без шифрования — приложение
персональное, не публикуйте файл `data/`.

### Mock

Провайдер с типом «Mock» отвечает фиксированными действиями — удобно, чтобы
проверить движок и интерфейс до подключения реальной модели.

## Как играть самому (режим человека)

1. При создании персонажа включите «Этот персонаж — вы». Модель не нужна;
   инструментами станут те, что вы ему назначите.
2. Добавьте его в сцену к ИИ-персонажам. Внизу комнаты сцены появится тоггл
   «кто говорит»: 🎬 Режиссёр (архитектор: события и указания) или любой
   персонаж сцены (в т.ч. ИИ — режим кукловода).
3. В режиме персонажа: текстовое поле отправляет реплику от его имени,
   кнопка «Действие» открывает диалог инструментов — поиск, карточки с
   видимостью, форма аргументов по JSON-схеме, эффекты применяются как у ИИ.
4. Галочка «пауза для человека» (в настройках сцены или при создании) —
   сцена сама встаёт на паузу после каждого круга ИИ и ждёт вашего хода.

## Как это работает

```
ход персонажа:
  1. Сборка его личного контекста:
       system: persona + сцена + участники + его состояние + правила
       история: только видимые ему события (его реплики/действия как assistant
       с tool_calls + tool-ответы, чужое — как user-сообщения)
  2. Вызов его модели: tools + tool_choice=auto (native function calling)
  3. Исполнение tool-вызовов: валидация аргументов, разрешение получателя,
       эффекты на state, запись события с аудиторией видимости
  4. Продолжение итераций (модель может добавить реплику после действия)
  5. Ход следующего персонажа
```

Каждый вызов модели логируется (`api_logs`): точный запрос и сырой ответ —
в live-комнате по кнопке `{}` у любого события. Это ваш главный инструмент
для разбора, «что модель думала».

  app/

## Защита бюджета и от спама

- **Лимит вызовов API** на сцену (по умолчанию 300) и **лимит токенов**
  (1 000 000): при исчерпании сцена автоматически встаёт на паузу со
  системным событием. Счётчики видны в шапке live-комнаты, лимиты меняются
  в настройках сцены.
- **Анти-повторы**: то же действие с теми же параметрами несколько раз
  подряд — модель получает предупреждение в tool-ответе; на третьем повторе
  сцена ставится на паузу.
- **Авто-пауза при ошибках**: 5 неудачных ходов подряд (упавший провайдер,
  таймаут 3 минуты) — сцена встаёт на паузу.
- **Пауза между итерациями** и между ходами — модель не молотит запросы.

## Скоринг: схемы валидации

«E2e-тесты» для персонажей: цепочка шагов из tool-вызовов, привязанная к
участнику **конкретной сцены** (у каждого — своя схема; персонажи о ней не знают).

- **Шаг** = `{инструмент, обязательный?, баллы, мин. количество, фильтр по аргументам}`.
- Порядок важен: шаг засчитывается вхождением **после** всех предыдущих
  обязательных шагов. Вхождение раньше места в цепочке («поцелуй раньше кофе») —
  нарушение со штрафом. Необязательный шаг — бонус: пропустил, просто без баллов.
  Провал обязательного шага рвёт цепочку — дальнейшее не засчитывается
  («от секса к кофе нельзя»).
- **Запрещённые инструменты** — нарушение за каждое вхождение.
- Итог: `Σ баллов засчитанных − штраф × нарушения`, % обязательных шагов,
  статистика вызовов (количество, ходи первого/последнего).

Схемы создаются в разделе «Схемы», привязываются к участникам при создании
сцены. Оценка — кнопка 🏆 в шапке live-комнатры (пересчитывается на лету,
можно смотреть и до завершения сцены). API: `GET /api/scenes/:id/scores`.

**Переоценка завершённой сцены**: скоринг считается по логу событий в момент
запроса, поэтому правка схемы валидации (шаги, баллы, штрафы) после завершения
сцены меняет оценку при следующем пересчёте — и в комнате сцены, и в отчётах
прогонов сценариев. Схему можно перепривязать к участнику и у завершённой
сцены (PATCH `/api/scenes/:id`).

## Сценарии: канвас цепочек сцен

Раздел «Сценарии» — граф, где узлы это сцены, а рёбра задают порядок и
**условия перехода**. Прогон («ран») проводит выбранный состав персонажей
по цепочке: кто выполнил условия — идёт дальше, кто нет — выбывает.

- **Узлы**: `сцена` (запускает свою сцену для пришедших; опция «сброс при
  входе» — свежий заход вместо продолжения), `финал` (терминал успеха, бонус
  очков), `выход` (терминал провала; флаг «остановить всё» завершает прогон
  сразу). Бонус узла начисляется за само его достижение — «дошёл до финала»
  конвертируется в очки.
- **Ребро** = правило перехода: приоритет (меньше — проверяется раньше) и
  условия, объединённые по «И». Первое подошедшее ребро побеждает; не подошло
  ни одно — персонаж остаётся в узле, пока вы не решите вручную.
- **Условия** (машиночитаемые правила вызова тулов):
  - `шаг` — персонаж успешно вызвал инструмент (с фильтром по аргументам):
    «Саша обязан поцеловать Яну» = шаг `kiss` с фильтром «Яна», закреплённый
    за Сашей;
  - `скор / % схемы` — оценка по привязанной схеме валидации (порог);
  - `без нарушений` — ноль нарушений схемы в сцене;
  - `ключ состояния` — числовая проверка `state` персонажа (`mood >= 1`).
  Условие можно закрепить за конкретным персонажем (тогда оно проверяется по
  его действиям для всех переходящих) или оставить личным для каждого.
- **Прогон**: входной узел стартует сразу, сцены узлов запускаются движком
  (бюджеты и анти-спам работают как обычно). Переходы оцениваются
  автоматически при завершении сцены (maxTurns или «Стоп») или кнопкой
  «Оценить переход». Между сценами каждый персонаж получает личный рекап
  увиденного (director-событие) — примитивная память; на узле с включённым
  «течением времени» персонажам начисляется их доход.
- **Отчёт**: кто дошёл до финала, кто выбыл, очки за сцены (живой пересчёт
  по схемам — правка схемы меняет отчёт) + бонусы узлов. Итог = Σ скоров
  посещённых сцен + Σ бонусов.

Один ран — один прогон; сцена не может одновременно стоять в двух узлах
графа (revisit делайте отдельной сценой-копией с «сбросом при входе»).

## Заявки агентов на новые инструменты

Опция сцены «Разрешить агентам просить новые инструменты» добавляет каждому
агенту виртуальный инструмент `request_tool`. Не найдя нужного действия,
агент описывает черновик (имя, JSON-схему параметров, видимость, шаблон
наблюдения, эффекты, цену) и причину — заявка падает в очередь (панель 📥
в шапке live-комнаты, обновляется по SSE).

- Заявка — скрытое действие (`audience: none`): другие персонажи её не видят,
  проситель видит в своей истории как обычный tool-вызов.
- Черновик проходит структурную проверку (согласованность аудитории,
  targetParam, эффектов и плейсхолдеров со схемой) — кривые даже не попадают
  в очередь: модель получает ошибку в tool-ответе и исправляется.
- **Одобрить** — инструмент создаётся в БД (`origin: от агента`), назначается
  просителю и доступен уже со следующего хода (движок перечитывает тулы из БД
  каждый ход; паузить сцену не нужно). **Отклонить** — с причиной. Решение
  приходит персонажу личным событием от Архитектора.
- Безопасность: инструмент — это декларативные данные (схема/видимость/
  эффекты), а не код; агент физически не может предложить ничего, что не
  умеет существующий исполнитель `executeTool`.

## Экономика: деньги, магазин, характеристики

- **Цена инструмента** (`$` в редакторе тулов) списывается с ключа `money`
  состояния актёра; при нехватке денег действие не выполняется — модель
  получает отказ с остатком баланса. Цена автоматически дописывается в
  описание тула для модели, а системный промпт объясняет правила трат.
- **Доход** (поле персонажа, `$/период`) начисляется на `money` при переходе
  между узлами сценария с включённым «течением времени» — узлы графа задают
  ход времени: «кафе → дом» = месяц прошёл.
- **Характеристики** (раздел «Характеристики»): реестр полей персонажей —
  рост, вес, физподготовка, красота, настроение, деньги… В редакторе
  персонажа это обычные поля ввода (выбор для вариантов, числа с
  диапазоном), а не голый JSON; ключи эффектов в тулax, товарах и условиях
  переходов выбираются из этого же реестра.
- **Магазин** (раздел «Магазин»): товары — простые карточки (название, цена,
  описание, категория, эффекты), а не инструменты. Агентам не нужно
  назначать ничего вручную: пока в магазине есть товары, у каждого агента
  появляются два встроенных тула — `shop_browse` (посмотреть ассортимент и
  цены, бесплатно) и `shop_buy` (купить; для подарка — имя получателя в
  параметре `for`). Покупки видны в схемах валидации и условиях переходов
  как обычные шаги. Товары заявками `request_tool` не создаются — агент
  смотрит витрину и решает сам.
- **Отложенные товары**: поле «применится через N сцен». Деньги списываются
  сразу, а эффект наступает после N переходов между сценами сценария —
  и только если агент до них дойдёт. Помада действует сразу, операция —
  через две сцены: агент вынужден выбирать между маленькой выгодой сейчас
  и большой в перспективе. О наступлении эффекта персонаж получает личное
  уведомление вместе с рекапом новой сцены.

## Место сцены и публичность характеристик

- **Место действия** (поле «Место» в настройках сцены): «дом», «улица»,
  «кафе», «отель»… Попадает в промпт всем участникам («Место: дом») и
  используется правилами границ (requirePlace) и одежды (undressPlaces).
- **Публичные характеристики** (реестр, флаг «видно окружающим») показываются
  в промпте каждого участника одной строкой: `👩 Яна — Рост: 172 см,
  Красота: 8…` (не более 8 ключей, чужие деньги не подсматриваются).
- **Скрытые характеристики** («скрытая» в реестре) не показываются никому,
  кроме владельца. Дальше — см. «Знания и ложь».

## Отношения

- Отношение — направленное чувство «насколько X расположен к Y» (матрица в
  таблице `relations`). Агент видит только **свои** чувства («# Твоё
  отношение к другим: Саша 3»); чувства других к себе — не видит, только их
  поступки.
- **Эффект `relation`** у инструментов и товаров: «отношение получателя к
  актёру +N» (цветы: Яна→Саша +1). Разрешён только адресным тулам
  (audience=target); изменения пишутся в событие (`relationChanges`) и в
  ответ модели («Отношение Яны к тебе: +1 (теперь 3)»).
- **Условие перехода флоу** `relation`: «отношение Яны к Саше ≥ 5» —
  чьё (`whoseId`, пусто = переходящий) и к кому (`toId`), порог. В отчёте
  прогона у каждого персонажа строка итоговых отношений.

## Границы персонажа (согласие)

- У персонажа есть список **правил-границ** (редактор персонажа, секция
  «Границы»): на какой адресный инструмент (`*` = любой) и с какими
  условиями: `minRelation` (отношение владельца к актёру), `minMood`,
  `requirePlace` (место сцены) и `requireAttr` — требование к **истинной**
  характеристике актёра или владельца (проверяется физикой, заявления
  не считаются).
- Проверка — в единой точке исполнения (`executeTool`), **до** денег и
  эффектов: модельный вызов и ручной act проходят одни и те же границы.
  Отказ fail-closed: действие не исполняется, деньги целы, `ok:false`
  (скоринг его не засчитает), применяются «последствия отказа» (эффекты
  правила: отношение владельца к актёру −N, настроение владельца; на
  актёра система не давит — только его собственные решения).
- Попытка автоматически видна владельцу границы: событие с аудиторией
  [владелец] и наблюдением «Саша пытается: Поцелуй — но Яна мягко
  уклоняется…». Актёр получает текст отказа от лица персонажа и совет
  сменить тактику. Границы **никогда не показываются в промптах** — агент
  узнаёт о них, только столкнувшись.
- Настойчивость гасит анти-спам движка: 3 одинаковых вызова подряд — пауза
  сцены. Граница инициатора не проверяется: если владелец правила сам
  вызывает инструмент, он действует по собственному решению.

## Знания и ложь

- Истина о скрытых характеристиках хранится у владельца (state), заявления —
  у наблюдателя (таблица `knowledge`, `claimed | verified`). Инвариант:
  **истина о скрытом не попадает ни в один промпт без verified-записи у
  этого наблюдателя.**
- Виртуальный тул `reveal_attribute` (появляется у агентов, когда в реестре
  есть скрытые характеристики): заявить о своей характеристике — лично
  (`to: имя`) или всем. Значение **не сверяется** с истиной: можно и лгать.
  Наблюдатель запомнит: в его промпте появится «Достоинство: по словам
  Саша — 18 (не проверено)».
- **Проверка** (физика: обнажение, requireAttr) ставит `verified` с истинным
  значением. Если прошлое заявление расходилось — разоблачение: личное
  событие наблюдателю («Ты видишь собственными глазами…») и штраф
  отношению по `liePenalty` атрибута (в реестре, дефолт 2). Повторная
  проверка без нового заявления не дублирует разоблачение; `verified`
  остаётся в памяти навсегда (видел — видел).

## Одежда

- **Реестр слотов** (раздел «Характеристики», низ страницы): `top`,
  `bottom`, `underwear`… у каждого слой (`layer`: 1 верхнее, 2 бельё) и
  места, где слот можно обнажить (`undressPlaces`, пусто = где угодно).
- Ношение — плоские ключи state: `worn_top: "Рубашка"`. Снятое —
  `carried_top` (предмет при вас, `wear` вернёт). Виртуальные тулы
  `undress {slot}` / `wear {slot}` доступны всем, пока в реестре есть слоты.
- Физика без флагов: нельзя снять нижнее, пока надето верхнее (по слоям);
  нельзя обнажиться не в своём месте («на улице так не делают»). Успешное
  обнажение слота **верифицирует** скрытые характеристики, которые он
  прикрывал (`coveredBy` у атрибута), для всех присутствующих — ложь
  вскрывается в тот же момент (см. «Знания и ложь»).
- **Одежда в магазине**: товар с заполненным «слотом» при покупке сразу
  надевается на владельца (получателя подарка).

## Навыки

- **Навык** (раздел «Навыки»): то, что персонаж умеет — поцелуи, секс,
  готовка, вождение. Ключ, название, макс. уровень и галочка **«может
  развиваться практикой»** (появляется поле «применений на уровень»).
- По галочке система **сама создаёт скрытую характеристику** `skill_<ключ>`
  (0…макс): вручную в реестр лезть не нужно. Уровень виден только владельцу
  (своё состояние в промпте); партнёры видят только последствия действий —
  «поцелуй оценивается по факту». Похвастать уровнем можно через
  `reveal_attribute` — но это заявление со слов (см. «Знания и ложь»).
- **Практика**: у тула есть поле «тренирует навык». Каждые N **успешных**
  (`ok:true`) применений поднимают уровень актёра на +1 (до максимума),
  счётчик хранится отдельно (`skill_practice`), отказы и спам не качают
  (границы — `ok:false`, анти-повтор — пауза сцены). При росте уровня
  персонаж получает личное уведомление («Практика: навык … вырос»),
  которое не видно партнёрам. Параллельный путь — товары-курсы: товар с
  эффектом `skill_sex +1` и задержкой в сценах («учёба занимает время»).
- Уровни у конкретного персонажа — обычные поля в группе «Навыки» его
  редактора (можно выдать «опытного» персонажа сразу).
- Тулы навыком **не гейтятся**: секс доступен и с уровнем 0 — просто
  исход будет унылым (исходы/условия — следующий слой, см. «Куда
  масштабироваться»). Жёсткое требование уровня оставлено на будущее для
  другого рода действий (водить машину, готовить ужин).
- **Клампинг характеристик**: эффекты инструментов, покупок и границ
  зажимают значения по `min`/`max` реестра — настроение не уедет за 10.

## Исходы действий

- **Исход** (у тула, раздел «Исходы» в редакторе): `условия («И») → эффекты
  поверх базовых + личная заметка цели`. Проверяются по **истинным**
  значениям на момент действия (навык актёра, атрибуты, отношение цели,
  место, слоты одежды цели, химия); побеждает первый подошедший.
- Пример оргазма: `have_sex` с исходом «кульминация»
  `[skill_sex ≥ 3, достоинство ≥ 18, отношение ≥ 5]` → mood +3,
  relation +2, химия +1, заметка цели «волна накрывает»; исход «не то»
  `[skill_sex < 1]` → mood −1, frustration +1. Требование `worn_underwear
  = ""` закрывает «секс в джинсах» — физика.
- Заметка цели доставляется лично (director-событие только ей) — партнёр
  переживает исход, не видя чисел. id сработавшего исхода пишется в событие:
  виден в транскрипте и доступен условию флоу
  `{type: "outcome", toolName, outcomeId}` — «финал только после оргазма».
- **Скрытые требования**: галочка «скрыть требования» убирает исход из
  описания тула — модель узнаёт по факту. Открытые исходы, наоборот,
  дописываются в описание (движок собирает текст сам: «„кульминация“:
  твой навык „Секс" ≥ 3, …»).

## Химия пары

- Симметричная скрытая матрица −3…+3 (дефолт 0), никому из агентов не
  видна — узнают «по факту». Редактируется в карточке персонажа
  («Химия с другими»).
- **Множитель отношений**: эффекты на отношение умножаются на
  `1 + химия/2`: при +2 комплимент `+1` даёт `+2`, при −2 гасится в ноль.
  Работает у тулов, исходов и подарков.
- **Растёт от удачных исходов** (эффект `химия ±N`): любит → получается
  лучше → любят сильнее — самоусиливающаяся спираль.

## Куда масштабироваться (задел уже есть)

- **Память/суммаризация**: сейчас в контекст идёт окно последних событий
  (`contextEvents`). Точка расширения — `src/lib/prompt.ts:buildMessages`:
  старые события можно сжимать в summary тем же персонажем.
- **Скоринг**: все события и логи уже структурированы — судью/чеклисты можно
  добавить как отдельный модуль поверх `events` + `api_logs`.
- **Мир**: время/локации/предметы — это state + инструменты; движок менять не нужно.
- **Параллельные сцены**: движок держит Map сцен, ограничений нет.
